# Передача проекта разработчику — версия 0.5.0

Рабочая ветка: `codex/culinary-updates`. Контрольная версия: тег `v0.5.0`.
Изменения подготовлены для ревью в `main`, автоматического слияния нет.

## Код и запуск без реальных данных

```powershell
git clone --branch codex/culinary-updates https://github.com/khrustand/purchase-forecast-service_xb.git
cd purchase-forecast-service_xb
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m unittest
```

Backend требует Python≥3.11, только стандартную библиотеку. Для разработки
рекомендуется3.12. Тесты используют синтетические XLSX, не требуют .env,
пользовательских выгрузок, сети и доступа к Supabase. Проверки GitHub Actions
запускаются на Python3.11/3.12 под Windows и Linux.

## Продолжить с теми же отчетами и меню

В Git нет реальных XLSX, .env, ключей, локальных реестров и аналитических
результатов. Владелец передает отдельный приватный ZIP со снимком данных.
Распаковать его **вне клона**, например в `C:\PrivateData\purchase-forecast`.
Из папки кода:

```powershell
.\.venv\Scripts\python.exe -m scripts.run_handoff --root C:\PrivateData\purchase-forecast --verify-only
.\.venv\Scripts\python.exe -m scripts.run_handoff --root C:\PrivateData\purchase-forecast
```

Открыть http://127.0.0.1:8000. При занятом порте добавить `--port 8002`.
Это отдельная копия: хранилище локальное, cloudключи не нужны, .env не
загружается. Сервер доступен только на этом компьютере. Изменения отчетов
и меню затрагивают распакованную копию, не рабочую базу владельца.
Сеть может использоваться для открытого прогноза погоды; изменение погоды,
текущего времени и новых данных естественно меняет прогноз.

`--verify-only` проверяет исходный снимок до редактирования. После добавления,
удаления или изменения файлов проверки первоначальных хэшей могут не пройти.

Структура снимка:

- `reports/` — все активные отчеты из Supabase и локальных дополнений в одном
  локальном реестре с сохраненными ID, датами и исходными именами.
- `localappdata/PurchaseForecastService/` — актуальные меню и справочник
  кандидатов/приоритетов тестовых блюд.
- `menu-state.json` — ручные исключения и типы производства.
- `weather.json`, если доступен, — публичный кэш погоды.
- `reference/` — прежние локальные выгрузки, результаты расчетов и контекст
  Codex для справки; эти файлы не подключаются вместо активного реестра.
- `snapshot.json` — ревизия кода, время снимка и SHA256 всех включенных файлов.

Для Codex текущие правила и контекст лежат в `reference/.codex/` снимка.
Их можно перенести в локальную `.codex/` клона после проверки существующих
файлов; чужой локальный контекст не перезаписывать без просмотра.

Новый снимок владелец может создать так:

```powershell
.\.venv\Scripts\python.exe -m scripts.export_handoff --output C:\PrivateData\handoff.zip
```

Экспорт читает рабочую базу, но не меняет ее. По умолчанию настройки читает
из AppData, иначе из .env проекта; можно указать `--env-file`. Секреты в ZIP
не включаются. Архив содержит коммерческие данные: передавать другу отдельно,
не помещать в публичный репозиторий, PR или Release.

## Зафиксированные правила продукта

- Матрица:32поставляемых блюда, ТТ отдельно. Каталог меню включает все
  активные строки, в том числе без количеств; «снято» исключается.
- ПоставкиПн/Ср/Пт до открытия, заказD−2до18:00МСК. Онигири/темаки/блины2дня,
  остальные поставляемые3дня; овсяная/рисовая/омлет/сырники/запеканкаТТ1день.
- Питание5порций в день по всему ассортименту, отсутствует в реализации,
  учитывается отдельными актами и исключается из KPI списаний.
- Общая цель2%: себестоимость потерь кулинарии+снеков+выпечки+кондитерки+хлеба
  / общая выручка. Отдельный лимит кулинарии по выручке предварительный.
- Единый расчет спроса и риска: [описание](demand-balance.md). Стартовые
  параметры85% желаемого наличия и5% допустимой цены резерва в модельном
  результате. Партии и обычный минимум3 пока не ограничивают потребность.
  Тестовые блюда без истории — по3порции, их риск/прибыль не выдумываются.

## Ограничения, которые нельзя потерять

- Время окончания наличия и замены блюд гостями неизвестны; скрытый спрос
  не восстановлен. Сценарии+10/+20% — предположения. Остаток не всегда порча.
- Фактический доступный остаток перед заказом пока не вычитается; отработанный
  процесс пользователя не менять без его запроса.
- Чеки и подробные акты пока хранятся локальными дополнениями. SQL003
  подготовлен, но не применен. Для переноса их в Supabase нужны и миграция,
  и перенос реестра/файлов, и изменение адаптера. Не выполнять SQL вслепую.
- iiko не подключен, права в нем только на чтение. Снеки входят в общий
  контроль потерь, их ассортимент/производство пока не планируется.
- В web_server.py есть старые переопределенные рендереры; работает последнее
  определение. Не менять первый найденный вариант, предполагая, что он активен.
- Публичные сборки не должны включать реальные прошлые заказы. Сборщик
  исключает их по умолчанию; флаг `-IncludeLocalOrderHistory` только для
  осознанной приватной сборки, которую нельзя публиковать в GitHub.

Для живого общего Supabase доступ предоставляется владельцем отдельно,
через защищенную передачу настроек. Воспроизводимый снимок позволяет начать
разработку без этих ключей и без риска изменить рабочие отчеты.
