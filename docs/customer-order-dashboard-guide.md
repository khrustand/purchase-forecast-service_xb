# Руководство для заказчика: окно заказа кулинарии

## Назначение окна

Окно заказа кулинарии помогает принять решение, сколько готовых блюд заказать в кофейню на ближайшие рабочие интервалы. Сервис работает только с кулинарией: супы, горячее, завтраки, салаты, роллы и близкие готовые позиции.

Главная цель - не заменить решение управляющего, а дать прозрачную рекомендацию: что заказать, где есть риск списаний, какие позиции лучше держать постоянно, а какие оставить в ротации.

## Какие данные использует сервис

Сервис берет данные из трех источников:

| Источник | Для чего нужен |
| --- | --- |
| Продажи | Понять реальный спрос по каждой позиции и по дням недели. |
| Акты списания | Найти позиции, которые часто не продаются и создают риск перепроизводства. |
| Сроки годности | Не заказывать запас больше, чем позиция может безопасно храниться. |

Дополнительно сервис учитывает погоду в Санкт-Петербурге: температуру и наличие осадков. Погода используется как мягкая корректировка, а не как главный источник прогноза.

## Как строится заказ

Заказ строится по рабочему календарю кофейни:

| Окно заказа | Какие дни покрывает |
| --- | --- |
| `Пн+Вт` | понедельник и вторник |
| `Ср+Чт` | среда и четверг |
| `Пт+Сб+Вс` | пятница, суббота и воскресенье |

Для обычных двухдневных окон сервис считает спрос на 2 дня.

Для окна `Пт+Сб+Вс` сервис не увеличивает количество линейно на 3 дня. История показала, что это дает перебор. Поэтому для выходного окна используется другое правило:

- объем держится ближе к двухдневному заказу;
- третий день закрывается не большим количеством, а более подходящим ассортиментом;
- приоритет получают позиции со сроком годности 3 дня;
- позиции со сроком 2 дня не получают запас на третий день;
- итоговый объем ограничивается историческим верхним уровнем продаж по уикендам.

## Верхние показатели экрана

| Поле | Что означает |
| --- | --- |
| `Период анализа` | Даты, за которые сервис взял продажи и списания. |
| `Меню` | Сколько позиций собрано из целевой витрины. Цель сейчас - 34 позиции. |
| `Объем заказа` | Сумма штук по текущей базовой рекомендации. |
| `Недобор до цели` | Сколько позиций не хватает до целевого меню 34 позиции. |
| `Резерв с высоким риском` | Сколько позиций попало в меню только как резерв из-за риска списаний. |
| Карточки категорий | Сколько позиций и штук приходится на каждую категорию. |

## Блок `Будущие заказы по датам`

Это главный рабочий блок. В нем показаны будущие интервалы заказа.

В заголовке каждого интервала указано:

| Поле | Что означает |
| --- | --- |
| Название окна | Например, `Ср+Чт` или `Пт+Сб+Вс`. |
| Даты | Какие календарные дни покрывает заказ. |
| Общее количество | Сколько штук сервис предлагает заказать по этому окну. |
| Правило окна | Объясняет, обычное это двухдневное окно или трехдневное окно с ограничением объема. |
| Сроки годности | Сколько позиций в заказе имеют срок 3 дня и сколько - 2 дня. |
| Погода | Прогноз или погодная разметка по дням окна. |
| Прошлое сопоставимое окно | Интервал, с которым сравнивается будущий заказ. |

Например, для `Пт+Сб+Вс 2026-08-07..2026-08-09` прошлым сопоставимым окном будет `2026-07-31..2026-08-02`.

## Поля таблицы будущего заказа

| Поле | Что означает | Как читать |
| --- | --- | --- |
| `Позиция` | Название блюда и категория. | Показывает, что именно предлагается заказать. |
| `Заказ` | Рекомендованное количество на выбранное окно. | Это итоговое число для заказа по позиции. |
| `Срок` | Срок годности позиции в днях. | Для окна `Пт+Сб+Вс` безопаснее позиции со сроком 3 дня. |
| `Продажи прошлого окна` | Сколько штук этой позиции продалось в прошлом таком же интервале. | Помогает сравнить рекомендацию с последним фактом. |
| `Списания прошлого окна` | Сколько раз позиция попала в акты списания в прошлом таком же интервале. | Если списания есть, позицию стоит проверить особенно внимательно. |
| `Риск` | Уровень риска списаний и причины. | Показывает общий риск по истории и свежий сигнал прошлого окна. |
| `Решение` | Рекомендованное действие по позиции. | Объясняет, держать позицию регулярно, ротировать, снизить запас или исключить. |

## Как читать `Заказ`

`Заказ` - это не простое повторение прошлых продаж. В него входят:

- средний спрос по истории;
- срок годности;
- риск списаний;
- день недели;
- погодная корректировка;
- ограничение для окна `Пт+Сб+Вс`;
- исторический потолок по выходным.

Если `Заказ` заметно выше продаж прошлого окна, нужно смотреть на `Риск`, `Списания прошлого окна` и `Решение`. Такая ситуация может быть оправдана, если позиция стабильная и хорошо продается в целом, но требует проверки, если в прошлом окне были списания.

## Как читать `Продажи прошлого окна`

Это продажи не за весь период анализа, а только за ближайший прошлый аналогичный интервал.

Примеры:

| Будущее окно | С чем сравнивается |
| --- | --- |
| `Ср+Чт 2026-08-05..2026-08-06` | `Ср+Чт 2026-07-29..2026-07-30` |
| `Пт+Сб+Вс 2026-08-07..2026-08-09` | `Пт+Сб+Вс 2026-07-31..2026-08-02` |
| `Пн+Вт 2026-08-10..2026-08-11` | `Пн+Вт 2026-07-27..2026-07-28` |

Это поле нужно для быстрой проверки: не предлагает ли сервис заказать сильно больше, чем реально продавалось в похожем прошлом окне.

## Как читать `Списания прошлого окна`

Это списания по позиции в ближайшем прошлом аналогичном интервале.

Важно: сейчас файл актов списания дает факт попадания позиции в акт, а не точное количество списанных штук. Поэтому значение означает количество попаданий позиции в списания.

Как трактовать:

| Значение | Что делать |
| --- | --- |
| `0` | Свежего сигнала списаний нет. Смотреть общий риск и продажи. |
| `1` | Есть повод проверить объем и остатки. |
| `2+` | Заказывать осторожнее, снизить запас или заменить позицию. |

## Как считается риск списаний

Риск считается по двум горизонтам:

| Горизонт | Для чего нужен |
| --- | --- |
| Весь период анализа | Базовый риск SKU. Показывает, часто ли позиция списывалась в принципе. |
| Прошлое сопоставимое окно | Свежий сигнал для конкретного заказа. Показывает, были ли проблемы именно в похожий период. |

Уровни риска:

| Риск | Условие | Что означает |
| --- | --- | --- |
| `высокий риск списаний` | Много списаний и слабый средний спрос. | Позицию лучше убрать из регулярного заказа или заказывать редко. |
| `средний риск списаний` | Списания встречаются часто. | Оставить можно, но без большого запаса. |
| `низкий риск списаний` | Списания встречались редко. | Держать под контролем. |
| `списаний не найдено` | В актах списаний позиция не найдена. | Риск по списаниям не подтвержден. |

## Как читать `Решение`

`Решение` - это рекомендуемое действие по позиции.

Возможные значения:

| Решение | Что означает |
| --- | --- |
| `держать регулярно, контролировать остаток каждый заказ` | Позиция важна для меню, ее стоит держать постоянно. |
| `заказывать осторожно, усиливать при росте продаж` | Позиция подходит для ротации, но не должна получать большой запас. |
| `оставить только в ротации, без страхового запаса` | Позиция может быть в меню, но небольшим объемом. |
| `заказывать реже или исключить из ежедневной витрины` | Позиция несет высокий риск списаний. |
| `не заказывать без ручной причины` | Недостаточно оснований для заказа. |

Под решением показывается основание: класс спроса, стабильность и срок годности.

## Классы спроса A/B/C

| Класс | Что означает |
| --- | --- |
| `A` | Самые значимые позиции по продажам. |
| `B` | Средний вклад в продажи. |
| `C` | Низкий вклад или слабая история. |

Класс не означает качество блюда. Он показывает только вклад позиции в продажи за анализируемый период.

## Стабильность спроса

| Значение | Что означает |
| --- | --- |
| `стабильный спрос` | Позиция продается регулярно и без сильных скачков. |
| `плавающий спрос` | Продажи есть, но заметно меняются по дням. |
| `рваный спрос` | Спрос сильно скачет. |
| `редкий спрос` | Позиция продавалась мало дней. |

Чем менее стабилен спрос, тем осторожнее нужно относиться к заказу.

## Блок `Ретроспектива прошлой недели`

Этот блок показывает, как модель сработала бы на прошлой неделе.

| Поле | Что означает |
| --- | --- |
| `факт` | Сколько реально продалось в этом окне. |
| `модель` | Сколько сервис предложил бы заказать по текущей логике. |
| `разница` | Модель минус факт. Плюс означает возможный перебор, минус - возможную нехватку. |
| `полный период в выгрузке` | Все дни окна есть в файле продаж. |
| Погода | Температура и условия в эти дни. |

Этот блок нужен, чтобы проверять доверие к модели. Если модель регулярно выше факта, заказ нужно ограничивать.

## Блок `Спрос по погоде`

Блок показывает, как продажи менялись при разных погодных условиях в Санкт-Петербурге.

| Поле | Что означает |
| --- | --- |
| `Месяц` | Месяц анализа. |
| `Погода` | Тип погодного условия: прохладно, умеренно, жара, осадки, жара + осадки. |
| `Дней` | Сколько дней попало в такую группу. |
| `Продаж/день` | Средние продажи в день по всем позициям. |
| `Супы`, `Горячее`, `Завтраки`, `Салаты` | Средние продажи по ключевым категориям в день. |

Погода не должна сама решать заказ. Она помогает понять, куда может сместиться спрос.

## Вкладки меню

| Вкладка | Что означает |
| --- | --- |
| `Постоянно` | Базовые позиции, которые стоит держать регулярно. |
| `Ротация` | Позиции для сменного меню и осторожного заказа. |
| `Резерв` | Позиции, которые можно использовать, если не хватает безопасных замен. |
| `Исключить` | Кандидаты на редкий заказ или временное исключение. |

Во вкладках `Продажи` и `Списания` показывают общий период анализа. Это нужно для оценки позиции в целом. В будущих заказах показывается прошлое сопоставимое окно, потому что там важно принять решение по ближайшему заказу.

## Практическое правило принятия заказа

Перед подтверждением заказа нужно пройти по шагам:

1. Проверить общий объем окна.
2. Для `Пт+Сб+Вс` убедиться, что объем не выше исторического потолка.
3. Отсортировать позиции с ненулевыми списаниями прошлого окна.
4. По ним проверить решение: снизить, оставить или заменить.
5. Проверить позиции со сроком 2 дня.
6. Проверить позиции, где заказ заметно выше продаж прошлого окна.
7. Подтвердить заказ или вручную скорректировать спорные позиции.

## Ограничения текущей версии

Сервис пока не учитывает остатки на витрине и складе, потому что их нет в текущей выгрузке. Когда остатки появятся, заказ должен считаться так:

```text
прогноз спроса
- текущий остаток
+ нужный страховой запас
= заказ
```

Также текущие списания считаются по факту попадания позиции в акт, а не по точному количеству списанных штук. Если в будущем появится выгрузка со штучными списаниями, риск станет точнее.
