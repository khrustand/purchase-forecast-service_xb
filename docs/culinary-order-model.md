# Модель заказов кулинарии

## Цель

Сформировать заказ кулинарии на ближайшие 2 дня по прошлым продажам, текущим остаткам и списаниям. Сейчас фокус только на кулинарии: обеды, салаты, роллы, супы, горячие блюда и похожие готовые позиции.

## Что прислать для первого расчета

Минимальный список позиций:

```text
sku,name,category,unit_cost,shelf_life_days,order_multiple
```

История продаж или заказов:

```text
date,sku,sold_quantity,waste_quantity
```

Остатки перед заказом:

```text
date,sku,stock_quantity
```

Дополнительные признаки дня:

```text
date,weekday,is_weekend,weather,comment
```

## Расчет

1. По каждой позиции берем продажи за последние периоды.
2. Списания считаем отдельным риском перепроизводства, а не прибавляем к спросу автоматически.
3. Считаем средний спрос на один день и стабильность спроса.
4. Умножаем на горизонт заказа: сейчас 2 дня.
5. Добавляем страховой запас по классу A/B/C и стабильности.
6. Уменьшаем или убираем страховой запас у позиций с частыми списаниями.
7. Проверяем срок годности: по умолчанию готовая кулинария считается на 3 дня, найденные 2-дневные позиции считаются без запаса сверх горизонта заказа.
8. Вычитаем текущий остаток, когда он появится в выгрузке.
9. Округляем до кратности заказа.
10. Помечаем причину: расчет по истории, риск нехватки, риск списаний, риск срока годности, нет истории продаж.

## Формула

```text
прогноз = среднее(продажи + списания) * 2 дня
страховой запас = прогноз * коэффициент запаса
сырой заказ = прогноз + страховой запас - остаток
итоговый заказ = округление вверх до кратности
```

Для текущей выгрузки по списаниям формула используется осторожнее:

```text
базовый спрос = среднее(продажи) * 2 дня
страховой запас = базовый спрос * коэффициент класса
если риск списаний высокий: страховой запас = 0
если риск списаний средний: страховой запас не выше 5%
итоговый заказ = округление вверх(базовый спрос + страховой запас - остаток)
```

Срок годности ограничивает расчет:

```text
если срок годности = 2 дня и горизонт заказа = 2 дня:
  страховой запас = 0

если срок годности = 3 дня и горизонт заказа = 2 дня:
  страховой запас разрешен по классу и стабильности спроса
```

Справочник `data/local/Хранение и сроки годности, реализации.xlsx` используется для сверки. Автоматически применяются только совпавшие сроки 2-3 дня или 48-72 часа. Более короткие сроки полуфабрикатов пока считаются производственной подсказкой и не применяются к готовому SKU без ручного подтверждения.

## Ротация меню

Целевая витрина на день: 34 позиции.

| Блок | Цель |
| --- | ---: |
| Супы | 8 |
| Второе / горячее | 9 |
| Завтраки и салаты | 17 |

Порядок отбора:

1. Внутри каждого блока позиции ранжируются по продажам, числу дней с продажами и штрафу за списания.
2. В основную витрину сначала попадают позиции без высокого риска списаний.
3. Позиции с высоким риском списаний используются только как резервная подмена, если безопасных SKU не хватает для закрытия квоты.
4. Если данных недостаточно для 34 позиций, отчет должен показывать фактический недобор, а не добирать случайные товары из нерелевантных категорий.

## Календарь заказа 2/2/3

Заказ строится не равными абстрактными периодами, а рабочими окнами кофейни:

| День заказа | Покрываемые дни | Горизонт |
| --- | --- | ---: |
| Понедельник | Понедельник + вторник | 2 дня |
| Среда | Среда + четверг | 2 дня |
| Пятница | Пятница + суббота + воскресенье | 3 дня |

Для 3-дневного окна `Пт+Сб+Вс` объем не масштабируется линейно на 1,5. Ретроспектива `2026-07-31..2026-08-02` показала явный перебор: 101 факт против 197 модельных штук. Поэтому правило изменено:

- общий объем держим близко к базовому заказу на 2 дня;
- третий день закрываем не увеличением количества, а расширением ротации;
- приоритет получают позиции со сроком годности 3 дня;
- позиции со сроком 2 дня не получают запас на третий день.
- итоговый объем дополнительно ограничивается историческим верхним уровнем по уикендам: сейчас это 75-й процентиль фактических продаж текущего меню, `129 шт.`.

## Погода и день недели

Погодная аналитика используется как корректировка к базовому спросу:

| Условие | Корректировка |
| --- | --- |
| Дождь | супы +10%, горячее +5%, салаты -5% |
| Жара от +27 | салаты +8%, супы и горячее -3% |
| Выходные | завтраки +5% |

Погода не заменяет продажи. Она только слегка двигает объем заказа, чтобы не ломать модель случайным прогнозом.

Для проверки гипотезы сервис дополнительно строит ретроспективу по погоде:

- берет все дни продаж из текущей выгрузки с 1 июня до последней даты, где есть реальные продажи;
- сопоставляет каждый день с архивом погоды по Москве;
- группирует дни по месяцу и типу погоды: `прохладно`, `умеренно`, `жара`, `осадки`, `жара + осадки`;
- для каждой группы считает средние продажи в день по всем позициям и отдельно по ключевым категориям: супы, горячее, завтраки, салаты;
- показывает этот разрез в интерфейсе рядом с ретроспективой заказов 2/2/3.

Пока город погоды зафиксирован как Санкт-Петербург. Когда появится точный адрес кофейни, город и ближайшую метеостанцию нужно вынести в настройку.

## Риск списаний

Текущий файл актов списания дает факт попадания позиции в акт, но не штучное количество по каждой позиции. Поэтому сейчас `waste_count` означает “сколько раз позиция встретилась в актах”, а не “сколько штук списано”.

Правила MVP:

| Условие | Риск | Действие |
| --- | --- | --- |
| 8+ попаданий и средние продажи ниже 1,5 шт./день | высокий | заказывать реже или исключить из ежедневной витрины |
| 5+ попаданий | средний | оставить, но без большого страхового запаса |
| 1-4 попадания | низкий | контролировать остаток |
| 0 попаданий | не найден | считать по обычной модели спроса |

В интерфейсе колонка `Риск` показывает не только уровень, но и основание:

- сколько раз позиция встретилась в актах списания;
- какой у нее средний дневной спрос;
- сколько дней позиция реально продавалась, если списаний нет.
- сколько списаний было в прошлом сопоставимом окне для конкретного будущего заказа.

Колонка `Решение` показывает действие и основание действия:

- класс спроса A/B/C;
- стабильность спроса;
- срок годности из файла сроков или правило по умолчанию.

Для расчета риска используется два горизонта. Весь период анализа дает устойчивый базовый риск SKU: позиция может регулярно попадать в списания, даже если в прошлую неделю списаний не было. Прошлое сопоставимое окно дает свежий сигнал для конкретного заказа: если в прошлом `Пт+Сб+Вс` позиция списывалась, текущий заказ по ней нужно снижать или заменять, даже если глобальный риск еще не высокий.

## Категории MVP

| Категория | Примеры |
| --- | --- |
| Обеды | обед с курицей, комплексный обед |
| Салаты | Цезарь, греческий, овощной |
| Роллы | ролл с курицей, ролл с тунцом |
| Горячие блюда | суп дня, паста, вторые блюда |

## Как учитывать погоду

Общий погодный коэффициент теперь рассчитывается по фактическим продажам: продажи каждого дождливого дня сравниваются со средними продажами сухих дней того же дня недели. Это отделяет эффект дождя от обычной разницы между понедельником, пятницей и выходными. Для безопасного заказа результат ограничивается диапазоном `0,70–0,95`: в день дождя общий клиентский поток и заказ уменьшаются на 5–30%.

После общей поправки применяется небольшое изменение структуры корзины: супы и горячее сокращаются слабее, салаты — сильнее. На панели будущих заказов для каждого дня показываются явление, температура, общий коэффициент трафика, процент изменения и погодный коэффициент каждой позиции.

Пустая ячейка или отсутствующий прошлый период не считаются нулевой продажей. Средние, стабильность спроса и погодные сравнения строятся только по реально присутствующим значениям. Явный числовой `0` в отчете сохраняется как подтвержденный факт нулевых продаж.

Окно `Пт+Сб+Вс` не ограничивается единым историческим потолком. Для каждой позиции пятница, суббота и воскресенье прогнозируются отдельно по имеющимся наблюдениям того же дня недели, затем складываются в общий заказ. Если истории конкретного дня недели нет, используется среднее только по существующим наблюдениям позиции. Для товаров со сроком годности 2 дня воскресный объем нужно привозить отдельным пополнением.

Погоду стоит добавлять после первых расчетов по истории. Начальная гипотеза:

- холод и дождь повышают спрос на супы и горячие обеды;
- жара может повышать спрос на салаты и роллы;
- сильный дождь может снижать общий трафик;
- выходные и события рядом могут менять спрос сильнее погоды.

Коэффициенты лучше подбирать по твоим фактическим заказам и продажам, а не задавать заранее.

## Переход к выпечке

После кулинарии отдельной моделью добавляем отпек:

- утренний стартовый отпек;
- дозаказ или второй отпек;
- списания на конец дня;
- зависимость от дня недели и погоды;
- отдельные правила для круассанов, слойки, десертов и хлебных позиций.
