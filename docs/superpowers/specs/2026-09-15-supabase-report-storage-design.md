# Supabase Report Storage Design

## Цель

Подключить сервис к Supabase так, чтобы загруженные XLSX-отчеты были доступны из любой точки, а существующая Python-модель прогнозирования продолжала работать без переписывания аналитики в SQL.

## Архитектура

В проекте остаются два режима хранения:

- `local`: текущий режим с файлами в `REPORT_UPLOAD_DIR` и `manifest.json`;
- `supabase`: оригинальные XLSX сохраняются в Supabase Storage, а метаданные загрузок сохраняются в таблице `uploaded_reports`.

Выбор режима выполняется через `STORAGE_BACKEND`. Web-сервер работает с общей поверхностью `list/save/resolve/paths`, поэтому страницы `/reports`, `/api/dashboard` и расчетная модель не знают, где физически лежит файл.

## Поток Данных

1. Пользователь загружает XLSX на `/reports`.
2. Сервис валидирует тип отчета, размер, расширение и ZIP-сигнатуру XLSX.
3. Сервис временно сохраняет файл локально, чтобы определить период через существующий парсер.
4. В режиме `supabase` сервис проверяет дубликат периода в `uploaded_reports`.
5. Файл отправляется в private bucket `uploads`.
6. Метаданные сохраняются в `uploaded_reports`.
7. При расчете сервис скачивает нужные файлы в локальный кэш и передает их существующей аналитике как обычные `Path`.

## Ошибки

Ошибки конфигурации Supabase показываются как понятные ошибки загрузки. Секреты не выводятся в интерфейс, логи или тесты. Локальный режим не требует Supabase-переменных.

## Проверка

Покрыть тестами:

- выбор локального или Supabase-хранилища по `STORAGE_BACKEND`;
- отказ при неполной Supabase-конфигурации;
- загрузку файла в fake Supabase Storage и запись fake metadata;
- скачивание файла через `resolve`;
- неизменность локального режима.
