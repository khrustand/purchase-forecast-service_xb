# Сервис заказов кулинарии

Для ежедневной работы начните с короткой инструкции: [Как пользоваться сервисом](docs/how-to-use.md).

Локальный сервис для формирования заказов кулинарии в кофейню: обеды, салаты, роллы, супы, горячие блюда и похожие позиции. Другие товарные группы сейчас не рассматриваются.

Главная задача MVP - по списку позиций и заказам за прошлые периоды собрать понятную рекомендацию: сколько заказать на ближайшие 2 дня, где есть риск нехватки, где вероятны списания и какие позиции требуют ручной проверки.

Выпечка будет следующим отдельным блоком: сначала разбираемся с кулинарией, затем переходим к отпеку.

## Технологический стек

| Слой | Технология |

| Веб-панель | Python 3.11, стандартный HTTP-сервер |

| Инфраструктура | Docker Compose, локальный запуск |

## Локальная установка

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m unittest
# Только если .env отсутствует:
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# При использовании нового шаблона заменить APP_PASSWORD в .env.
.\.venv\Scripts\python.exe -m scripts.run_local
```

Нужен Python 3.11 или новее; внешних Python-зависимостей нет. Активация
окружения не обязательна. Команда `scripts.run_local` загружает `.env`
из корня проекта (либо настройки из AppData, если `.env` отсутствует)
до инициализации хранилища. Остановка сервера: `Ctrl+C`.

После переноса на другой компьютер создайте `.venv` заново. Существующий
`.env`, локальные XLSX и отчеты сохраните. Если `python` не найден, укажите
полный путь к установленному Python при создании окружения. Docker нужен
только для альтернативного запуска через `docker compose up --build`.

Открыть веб-панель:

```text
http://localhost:8000
```

API:

```text
http://localhost:8000/api/dashboard
```

Ежемесячные отчеты:

```text
http://localhost:8000/reports
```

На странице можно загрузить XLSX с продажами или списаниями, увидеть определенный по книге период и скачать исходный файл. Загруженные месяцы автоматически объединяются в историю прогнозирования.

В разделах отчетов и меню можно выбрать несколько XLSX одновременно: до 100
файлов, не более 10 МБ на файл и 250 МБ суммарно. Можно загрузить ежедневные
отчеты сразу за весь месяц. В отчетах выбранный тип
«Продажи» или «Списания» применяется ко всем файлам пакета. Каждый файл
сохраняется отдельно: дубликаты и ошибки перечисляются по именам, успешные
загрузки сохраняются. Для файлов разных типов используйте отдельные загрузки.

## Кулинария ТТ

Вкладка **Кулинария ТТ** между заказами и аналитикой (`/production`) показывает
ежедневный план на 7 дней с даты начала расчета. В управлении меню включите
нужные позиции и задайте им тип «Собственное». План включает все такие позиции
из их групп меню, без квот и графика поставщика.

Количество — средние продажи соответствующего дня недели, умноженные на
погодный коэффициент и округленные до целого. Если истории этого дня недели
нет, берется среднее по доступным наблюдениям до начала плана. Будущие продажи
не используются; отсутствующие дни не подставляются как нули. Если продаж
нет вообще, отображается «нет данных». Остатки, списания и производственные
партии в этом ежедневном плане пока не учитываются — проверьте остаток перед
приготовлением. Тип «Собственное» в меню определяет состав плана; категория
отчета продаж сама по себе не переводит позицию в собственное производство.

## Погода в расчете

На рабочих вкладках показаны источник, время обновления, использование
устаревшего кэша и покрытие дат ближайшего заказа. В «Кулинарии ТТ» погода
показана для каждого дня, а коэффициент — для каждой позиции. В заказах
коэффициенты доступны в «Подробнее». Дождь корректирует поток, температура
и осадки — категории. При отсутствии прогноза на дату коэффициент равен 1.
Нейтральный коэффициент при доступном прогнозе означает, что условия не
требуют изменения количества. Надбавка выходного дня для завтраков больше
не выдается за влияние погоды; день недели учитывается историей продаж.

Также поддерживается суточный отчет продаж и маржи: период в строке
`За период: с ДД.ММ.ГГГГ по ДД.ММ.ГГГГ`, заголовки в четвертой строке,
колонки `Категория`, `Элемент номенклатуры`, `Количество`. Для прогноза
берется количество, включая продукцию с нулевой выручкой; строка `Итого`
исключается. Сводный отчет такого формата за несколько дней отклоняется:
в нем нет разбивки количества по дням. Исходный XLSX сохраняется целиком.

При удалении отчетов в Supabase учитывайте три места хранения:
Если запись отчета осталась в реестре, но файл невозможно скачать, приложение
пропускает его и показывает предупреждение «Расчет неполный» с именами файлов.
Неожиданные ошибки запроса возвращают страницу ошибки вместо пустого ответа.

При очистке учитывайте:
реестр `uploaded_reports`, объекты Storage и фрагменты `uploaded_report_chunks`.
Удаление только объекта Storage оставляет отчет в реестре; ранее скачанная
локальная копия может продолжать использоваться. После удаления записи
из `uploaded_reports` ее локальный кэш не участвует в списке и расчете.
В облачном режиме используются только загруженные отчеты Supabase. После
удаления продаж приложение ожидает новые данные; старые локальные XLSX
не подставляются. В локальном режиме при отсутствии загруженных отчетов
расчет может использовать XLSX из `data/local/`. Перед очисткой сохраните нужные исходники.

## Логика заказа

Сверка с меню показывает кулинарию: супы, горячее, салаты, завтраки, роллы,
снэки и категории с префиксом «Кулинария». Позиции, явно добавленные в меню,
учитываются независимо от названия категории отчета. Кофе, упаковка, выпечка
и прочие группы вне меню не входят в строки и итоги сверки. Полные исходные
отчеты сохраняются без изменений.

Для позиций, сопоставленных с управлением меню, расчет использует рабочую
группу блюда из меню (супы, горячее, салаты, завтраки, роллы), даже если
в отчете продаж указана общая категория «Кулинария производство».
Названия приводятся к названию меню, количества объединяются по датам.
Роллы участвуют в общей ротации с салатами и завтраками. Исходные XLSX
и их категории в базе при этом не изменяются.

Базовая формула:

```text
заказ = прогноз спроса на 2 дня + страховой запас - текущий остаток
```

После этого количество округляется до кратности заказа или производственной партии.

Срок годности ограничивает запас: готовая кулинария по умолчанию считается на 3 дня, а позиции со сроком 2 дня рассчитываются без страхового запаса сверх горизонта заказа.

Для первых расчетов нужны:

- список позиций: название, категория, срок годности, себестоимость, кратность заказа;
- продажи или заказы за прошлые периоды;
- остатки перед заказом;
- списания;
- пометки по дням: будни, выходные, погода, акции, локальные события.

## Управление меню

Раздел `Меню` в веб-интерфейсе собирает рабочий список блюд из XLSX-файлов прошлых заказов. Файл можно загрузить прямо на странице меню через блок `Добавить данные`; сервис сохранит его в локальную папку `Прошлые заказы` и сразу пересоберет список позиций. Сейчас используется лист `Кулинария`: именно эти позиции считаются обычным ассортиментом для заказа.

Требования к XLSX-файлу меню: лист должен называться с префиксом `Кулинария`, а внутри должны быть колонки `Артикул`, `Товар`, `К-во фасовок` или `Общее к-во`. Нечитаемые книги пропускаются и не ломают страницу меню.

Названия очищаются перед показом, но служебная звездочка `*` из исходного заказа сохраняется как признак `Собственное`. Такая позиция видна в общем меню и в сверке на главном экране, но не участвует в расчете заказа.

В таблице меню можно выключить позицию из прогноза или вернуть ее обратно. Расчет заказа берет только включенные позиции; отключенные блюда остаются видимыми в управлении меню, но не попадают в будущий список заказа. Локальное состояние хранится в `data/menu/menu-state.json` и не коммитится в git.

На основном экране блок `Сверка с меню` показывает, какая часть продаж попала в текущий расчет, какая осталась вне меню и какие позиции были выключены вручную. Это помогает отличить ошибку прогноза от ситуации, когда фактический заказ включает позиции, которых нет в загруженном меню или которые не сопоставились по названию.

При Windows-сборке папка `Прошлые заказы` автоматически добавляется внутрь приложения, если она есть в корне проекта во время сборки. Сами XLSX-файлы остаются локальными данными и исключены из репозитория.

## Диагностика проблем

| Проблема | Решение |
| --- | --- |
| Прогноз слишком ровный | Прислать продажи по нескольким прошлым периодам и дням недели. |
| Заказ завышен | Добавить остатки и списания. |
| Не видно риска нехватки | Добавить минимальный остаток и кратность заказа. |
| Не открывается веб-панель | Проверить `docker compose ps` и порт `APP_PORT`. |

## Supabase

Для облачного режима нужно один раз выполнить SQL из файла `supabase/migrations/001_uploaded_reports.sql` в Supabase SQL Editor и создать private bucket `uploads`.

После этого можно включить хранение отчетов в Supabase:

```env
STORAGE_BACKEND=supabase
```

В этом режиме оригинальные XLSX-файлы хранятся в Supabase Storage, а реестр загрузок хранится в таблице `uploaded_reports`. Расчетная модель продолжает читать файлы через тот же интерфейс, поэтому локальный режим остается запасным вариантом.

Если Supabase Storage обрывает загрузку большого XLSX, сервис сохраняет файл в таблицу `uploaded_report_chunks` небольшими частями и затем собирает его обратно при расчете. Для этого после `001_uploaded_reports.sql` нужно выполнить миграцию `supabase/migrations/002_uploaded_report_chunks.sql`.

## Облачный веб-запуск без Docker

Для работы независимо от компьютера сервис размещается как Render Python Web Service:

```text
GitHub -> Render Python Web Service -> Supabase
```

Render запускает приложение командой:

```powershell
python -m src.app.web_server
```

Постоянные данные остаются в Supabase, поэтому ноутбук в пекарне открывает только веб-адрес сервиса. Подробная инструкция: [docs/external-deployment.md](docs/external-deployment.md).

## Windows-приложение

Windows-выпуск работает как самостоятельное локальное приложение: запускается `purchase-forecast-service.exe`, поднимает сервер внутри процесса и открывает отдельное окно приложения через Microsoft Edge в режиме `--app`. В обычном сценарии пользователь не работает с адресной строкой `localhost` и не видит консоль. При закрытии окна приложения launcher останавливает локальный сервер и освобождает порт.

Сборка:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_windows.ps1 -InstallPyInstaller
```

Готовый файл:

```text
dist\purchase-forecast-service.exe
```

Установщик для чистой Windows-машины:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_installer.ps1 -InstallInno
```

Готовый установщик:

```text
dist\PurchaseForecastServiceSetup.exe
```

Этот файл можно перенести на новый компьютер с Windows и интернетом. Установщик не требует Python, Docker, VS Code или Android Studio: он ставит уже собранное приложение, создает ярлыки и предлагает запустить сервис сразу после установки.

Если Supabase уже настроен, exe сразу открывает главный экран заказов. Загрузка отчетов не является стартовым шагом: программа берет данные из подключенной базы и Supabase Storage.

Если настроек еще нет, exe откроет экран первичной настройки. На нем нужно один раз указать Supabase URL, secret key, bucket `uploads` и при необходимости логин/пароль входа в сервис. Настройки сохраняются локально:

```text
%APPDATA%\purchase-forecast-service\.env
```

Если рядом с exe положить `.env`, он будет иметь приоритет над AppData-настройками. Это удобно для переносного режима, но реальные ключи Supabase и пароль панели нельзя коммитить и нельзя отправлять в чат.
